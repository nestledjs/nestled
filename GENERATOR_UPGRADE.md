⏺ Generator Spec: Add _count Support for One-to-Many Relations

Overview

Modify the GraphQL fragment generators to automatically include _count fields for all one-to-many (list) relations in admin fragments. This enables the frontend to show relation counts without custom queries.

Current Behavior

Generated Fragment (user-fragments.graphql):
fragment __AdminUserDetails on User {
id
firstName
lastName
# ... all scalar fields
# Relations are NOT included
}

Problem: No way to know how many Organizations, Teams, etc. a User has without separate queries.

Desired Behavior

Enhanced Fragment:
fragment __AdminUserDetails on User {
id
firstName
lastName
# ... all scalar fields

    # NEW: Add _count for all one-to-many relations
    _count {
      organizations
      teams
      emails
      phoneNumbers
      addresses
      # ... all other list relations
    }
}

Technical Specification

1. Detection Logic

Identify One-to-Many Relations:
// In the generator code
field.relationName && field.isList === true

Examples from Prisma Schema:
model User {
organizations  OrganizationMember[]  // ✅ One-to-many (include in _count)
emails         Email[]               // ✅ One-to-many (include in _count)
activeOrganization Organization?     // ❌ One-to-one (skip)
primaryEmail   String?               // ❌ Scalar (skip)
}

2. Generation Rules

For __AdminXDetails Fragments:
- After all scalar fields are added
- Before the closing brace
- Add a _count block containing all one-to-many relation field names

Template:
// Pseudo-code for generator
function generateAdminDetailsFragment(model) {
const scalarFields = model.fields.filter(f => !f.relationName)
const listRelations = model.fields.filter(f => f.relationName && f.isList)

    let fragment = `fragment __Admin${model.name}Details on ${model.name} {\n`

    // Add scalar fields
    for (const field of scalarFields) {
      fragment += `  ${field.name}\n`
    }

    // NEW: Add _count block if there are list relations
    if (listRelations.length > 0) {
      fragment += `  _count {\n`
      for (const relation of listRelations) {
        fragment += `    ${relation.name}\n`
      }
      fragment += `  }\n`
    }

    fragment += `}\n`
    return fragment
}

4. Which Fragments to Modify

Modify:
- ✅ __AdminXDetails - Used in edit/detail pages (needs _count)
- ❓ __AdminXList - Used in list pages (optional, but useful)

Don't Modify:
- ❌ Regular (non-admin) fragments - Keep unchanged

Reasoning: __AdminXDetails is used in the edit page where we want to show "15 related Organizations" links. The list fragment could also benefit but is lower priority.

5. GraphQL Type Safety

Important: The _count field is automatically available in Prisma's GraphQL schema:

type User {
id: String!
name: String!
# ... other fields
_count: UserCount  # ← Auto-generated by Prisma
}

type UserCount {
organizations: Int!
teams: Int!
emails: Int!
# ... one Int field per list relation
}

No schema changes needed - Prisma already exposes this!

6. Edge Cases

Handle These:

1. No List Relations: Don't add empty _count {} block
# Country has no relations - no _count needed
fragment __AdminCountryDetails on Country {
id
name
}
2. Bidirectional Relations: Include both sides
   model User {
   teams TeamMember[]  // ✅ Include in User._count
   }
   model Team {
   members TeamMember[]  // ✅ Include in Team._count
   }
3. Self-Relations: Include normally
   model Category {
   children Category[]  // ✅ Include as _count { children }
   }
